## 六、今日思考题：第一版和你想象的差在哪

清单给的思考题是「**第一版跑起来的那一刻，和你原本想象的差在哪？**」——今天确实撞上了两个落差。

### 落差一：从「搜到所有书」到「自己一本本录入」

项目最早的想法是「**免费搜到各大 App 的所有书**」。Day 3 的研究把这条路否掉了（法律、技术、商业三条都走不通），Day 4 的 PRD 最终定为「**个人阅读记录工具**」——不提供书籍正文、不卖书、不做社交。

今天第一版跑起来，形态就是最初那个想法的**反面**：书要**自己一本本录**，封面要**自己找网址填**。没有任何"搜索"。

> 这不是做砸了，是**研究之后主动收窄**的结果。但"收窄"写在文档里是一行字，**跑起来才变成手感**——你第一次需要亲手敲进一本书名的那一刻，才知道这个产品到底是什么。

### 落差二：问题不在「功能少了」，在「我以为你知道该怎么点」

第一版跑起来后第一次试用，卡住的地方**不是缺功能，是两排长得一模一样的按钮**：

| 位置 | 长什么样 | 点了会怎样 |
| --- | --- | --- |
| 列表页顶部 | 全部 / 想读 / 在读 / 已读 | **筛选** —— 只看哪几本，一个字都不改 |
| 详情页书名下 | 全部 / 想读 / 在读 / 已读 | **改状态** —— 真的把这本书标成在读 |

点错了地方的后果，是「筛出来一片空白」，**看着像页面坏了**。而这个空状态，PRD 里恰好没规定（只规定了"一本书都没有"的空状态）。

> **这是设计者和使用者之间的信息差，只有真跑起来才会暴露。** 写 PRD 的时候，两排按钮在纸上只是两行文字；跑到浏览器里，它们才变成"我会点错的那个东西"。
>
> 补法：给筛选后为空的情况加了一句提示 + 一个「看全部」按钮。这属于 PRD 之外的细化，**明确不新开验收标准**（AC 仍是 23 条）。

### 一句话版本

> 第一版跑起来最大的落差，不是**功能比想象中少**，而是**问题比想象中"小"**——小到写文档时根本看不见，小到只有亲手点错一次才会发现。

## 七、今日卡点与解法

今天没有卡在半路的技术难题——产品代码只出过一次功能 bug（同毫秒排序，见本节末），其余时间基本都花在**验证**上。倒是「脚本报红」出现了四次，值得全部记下来——因为四次里有三次不是代码的错。

### 四次报红，三次是"报红的人"错了

| 第几次 | 现象 | 真正的问题在哪 | 处理 |
| --- | --- | --- | --- |
| ① | 浏览器冒烟页显示通过，但**只有 19 项**，我按另一支临时脚本的数字说成 20 项 | **数字搬运** —— 从"另一份文件"搬数字，没有回页面重数 | 改正为实测数字 |
| ② | 测试脚本报 `Cannot read properties of null` | **测试脚本自己写错**：`.progress-form` 是 class，我当成 id 查 | 改脚本，**没动一行产品代码** |
| ③ | app-flow 测试 5 项红 | **测试环境缺功能**：手写的事件 stub 没有冒泡 | 补上冒泡，5 项转绿 |
| ④ | 封面 2 项红（`getAttribute('src')` 返回 null） | **迷你 DOM 缺「属性反射」**：真浏览器里 `img.src = url` 会同步写进 HTML 属性，我的迷你 DOM 只挂在 JS 对象上 | 补上反射访问器，2 项转绿 |

**这四次合起来是一条教训**：

> **脚本报红，第一件事不是改代码，是确认「红的是谁」。** 四次里有三次，产品代码一动没动。

### 数字搬运这件事被升级成了硬规则

第 ① 次被你当场发现（你看页面数出 19 项，我说的是 20 项）。这条后来升级成了项目硬约束：

> **任何数字都不许从别处搬 —— 包括「条数 / 项数」。** 数字出处在哪，就回哪里实测一遍（`grep -c` / `wc -l` / `stat -c %s`），别用「另一份文件 / 另一支脚本」的计数顶替。

这是本项目**第二次**踩同类问题（Day 4 是行数没跟着补 AC 更新）。所以写这份日志时，所有行数、字节数、断言数都是**在最后一次改动之后重新测的**。

### 一个真实的功能 bug：同毫秒排序

写数据层时发现：连着写两条笔记，`createdAt` 可能**落在同一毫秒**，而排序又拿时间当依据 —— 谁先谁后就看运气了，最新那条可能排到后面去（违反 AC-15）。

**解法**：不用时间戳定先后，改用**写入顺序**（内部记一个自增的 `seq`，谁后写的数字大）。时间是"看起来该准"的东西，顺序是"一定准"的东西。

### 其余值得记的坑

| 坑 | 是什么 |
| --- | --- |
| 空作者显示「未填作者」 | 我照着 PRD 字面断言成空字符串 → 读源码改正。**PRD 的字面不等于代码的实现，以代码为准再回头核对 PRD** |
| `cards()[1]` 下标取书 | 列表是时间倒序，书变多之后**必然取错**。改成按书名定位 |
| 验证脚本随会话丢失 | 2c 阶段的临时脚本没留存，导致 AC-1~10 一度**没有自动化覆盖**，今天才补回来。**能复跑的验证要留下，别让它随会话消失** |

## 八、今日学到的

- **写得出来 ≠ 跑得起来。** 前面四天产出的全是文档，今天第一次产出"能点的东西"。同样是"做完"，验收方式完全不同——文档靠读，代码只能靠跑
- **测试的价值取决于它的环境有多真。** 后期把 DOM 从"手写镜像"换成"从真 `index.html` 解析"，立刻测出了 stub 测不到的东西（笔记不串书、删书零残留、刷新数据还在）
- **报红先问是谁的错。** 今天四次报红，三次是测试脚本或测试环境的毛病。养成"先定性、再动手"的习惯，能省下大量白改的代码
- **数字出处在哪就回哪里测。** 这条被写进项目硬约束了——因为它是唯一一个"错了也看不出来"的错误类型
- **时间是"看起来该准"，顺序是"一定准"。** 同毫秒排序的坑说明：拿一个不确定的东西当依据，功能就会时对时错
- **功能少了不致命，交互说不清才致命。** 第一版真正的第一反馈，是两排同名按钮——这只有真跑起来才暴露
- **研究阶段推翻的想法，会在开发阶段以"手感"的形式回来。** 「搜到所有书」在文档里被划掉是一行字，亲手敲书名的那一刻才是真的
- **入口要留得下。** 文档里写了"退路"，测试脚本却随手丢了——同样是"以后要用"，一个存下来了，一个没存
