## 0. 摘要

1. **整体形态**：纯前端应用——没有后端、没有数据库，双击 `index.html` 就能用。
2. **页面技术**：原生 HTML / CSS / JavaScript，零依赖、零构建。
3. **数据存在哪**：浏览器的本地存储（localStorage）。
4. **为什么能这么简单**：PRD 定了「单用户 + 无登录」，而这两条正好是后端存在的全部理由。
5. **代价**：数据只在这台电脑的这一个浏览器里，换浏览器或清缓存会丢。
6. **一条前提**：以「双击打开」的方式使用，代码**必须避开 ES Module**（`file://` 下模块加载会被拒），并且 localStorage 能不能用要先实测——见 2.11。

**一句话**：把数据层单独装进一个文件，其余全部做成静态页面——**这样第 23 天换数据库时，只改那一个文件**。

## 2. 技术路线

### 2.1 总览

| 层 | 选择 | 一句话理由 |
| --- | --- | --- |
| 整体形态 | 纯前端应用（无后端 / 无数据库） | 单用户 + 无登录，服务端的三条存在理由全部不成立 |
| 页面技术 | 原生 HTML + CSS + JavaScript | 零依赖零构建，不受校园网与代理劫持影响 |
| 数据存储 | 浏览器的本地存储 | 不需要启动任何服务，关掉浏览器数据还在 |
| 数据格式 | JSON 字符串 | 本地存储只能存字符串，结构化数据要先转换 |
| 数据出入口 | 一个独立的数据层文件，界面只通过它读写 | **第 23 天换数据库时只改这一个文件** |
| 页面组织 | 单个 `index.html`，三个视图切换 | 数据在内存里一份，切视图不用重新读 |
| 封面图 | 用户填网址，加载失败回退文字占位 | PRD AC-4 / AC-5 已定行为，这里定做法 |

### 2.2 为什么没有后端

Day 5 第一板块的结论，写进文档留档。典型网站需要后端的三条理由，逐条对照本项目：

| 典型网站需要后端的理由 | 本项目的情况 | 结论 |
| --- | --- | --- |
| 数据不能放在用户手里（前端代码用户改得动） | 数据是我自己的读书记录，改自己的数据没有任何收益 | ✗ 不成立 |
| 要区分「这是谁的数据」 | 无登录、单用户 | ✗ 不成立 |
| 数据要多人共享 | 不给别人看，只有我自己用 | ✗ 不成立 |

三条全部不成立，中间那层失去存在理由，数据库跟着一起省。

### 2.3 页面技术：原生三件套

**选什么**：HTML 写结构、CSS 写样式、JavaScript 写逻辑，三者都是浏览器自带的能力，不需要任何第三方库。

**为什么**：

1. PRD 6.3 第 4 条要求「页面自身的 HTML / CSS / JS 不引用任何外部地址」。用任何框架，要么引 CDN（外部地址），要么装构建工具，两条都违反。
2. 校园网 + Watt Toolkit 代理环境下，外部请求不可靠。（Day 1 已实测：GitHub 全站被本地代理劫持，`raw.githubusercontent.com` 完全取不到内容。）
3. 三个页面 + 一个数据层，原生 JS 完全够用。

**代价**：

- 没有框架的自动界面更新——改完数据要自己调用一个「重新渲染」的函数。多写几行，换来零依赖。
- 代码总量比用框架多一些，但项目本身小（预计 500–800 行）。

**什么时候可能得换**：将来如果要做多用户、云同步、复杂交互，会重写成前后端分离，那时再考虑框架。

### 2.4 数据存储：浏览器的本地存储

**是什么**：浏览器自带的一块键值存储区（localStorage）。每个来源（同一台电脑的同一个浏览器、同一个地址）有自己独立的一份，**关掉浏览器不会消失**。

**为什么**：

1. 不需要启动任何服务，双击页面就能读写。
2. 关掉浏览器再打开数据还在——直接满足 PRD 6.3 第 3 条。
3. 容量够用：浏览器一般给每个来源 5MB 左右，本项目存几十本书 + 几百条笔记远远用不完。

**代价（必须写清楚）**：

| 情况 | 结果 |
| --- | --- |
| 关掉浏览器、关掉电脑 | 数据**还在** |
| 换一个浏览器（Chrome → Edge） | 数据**不跟过去**，等于空白 |
| 清除「网站数据 / Cookie 及网站数据」 | 数据**丢失** |
| 重装系统、换电脑 | 数据**丢失** |
| 用无痕 / 隐私窗口打开 | 关掉窗口数据就没 |

> ⚠️ **PRD 验收标准里的「关闭浏览器再打开，数据都还在」满足。但「换浏览器 / 清缓存不丢」不在验收标准里，也确实做不到**——这是选这条路的代价，不是缺陷。

**什么时候可能得换**：要做多设备同步、要备份、数据量超过容量限制——第 23 天接数据库就是为这个准备的动作。

**出错兜底**：写入可能失败（无痕模式下不可写、容量满）。写入失败时**必须给出提示**，不能让界面看起来像存上了——对应 PRD AC-23（数据读写出错不能白屏）。

> ⚠️ 这条路上还有两个更靠前的前提：**`file://` 下 localStorage 的行为是未定义的**，能不能用必须实测；以及**代码不能写成 ES Module**，否则双击打开会白屏。两条都写在 **2.11**。

### 2.5 数据格式与唯一出入口

**存什么格式**：本地存储只能存字符串，所以书单和笔记都先转成 JSON 字符串再存，读出来时转回对象。

**存哪两个键**：

| 键名 | 内容 | 对应 PRD 字段 |
| --- | --- | --- |
| `reading:books` | 所有书籍（含阅读进度） | PRD 4.2 |
| `reading:notes` | 所有笔记 | PRD 4.3 |

> 加 `reading:` 前缀是为了避免和同浏览器下其他页面撞名。**阅读进度不单独存**——它是书的一部分（`currentPage` / `totalPages`），跟着书一起读写。
>
> 进度百分比也不存，按 PRD 3.2 的要求由「当前页 ÷ 总页数」实时算。

**唯一出入口**：所有对本地存储的读写，都走一个独立的数据层文件。界面代码**永远不直接碰本地存储**。

**为什么**：

- 换存储方案（第 23 天接数据库）时，只改这一个文件，界面代码一行不动。
- 出错处理、格式转换只写一遍，不在每个页面重复。

**数据层对外提供的能力**（具体命名 Day 7 定）：

| 针对 | 能力 |
| --- | --- |
| 书籍 | 新增 / 按 id 查 / 列出全部 / 修改 / 删除（连带删笔记） |
| 笔记 | 新增 / 列出某本书的全部 / 修改 / 删除 |
| 通用 | 读取失败时返回可识别的错误，不让界面白屏 |

### 2.6 代码分成几块

| 文件 | 管什么 | 依赖 |
| --- | --- | --- |
| `index.html` | 页面结构（三个视图 + 弹窗） | 无 |
| `styles.css` | 全部样式 | 无 |
| `store.js` | 数据层，唯一碰本地存储的地方 | 无 |
| `app.js` | 界面逻辑：读数据 → 渲染 → 接住点击 | `store.js` |

**为什么这么分**：`store.js` 不依赖任何东西，也不认识界面——所以它能被整体替换掉。`app.js` 认识界面和 `store.js`，是中间人。四个文件，没有第五个。

### 2.7 页面用什么渲染

**单页 + 三视图**。`index.html` 一个文件里放三个视图：

| 视图 | 对应 PRD | 切换方式 |
| --- | --- | --- |
| P1 书单页 | PRD 4.1 | 显示 / 隐藏切换，不做页面跳转 |
| P2 书籍详情页 | PRD 4.1 | 同上 |
| P3 添加 / 编辑弹窗 | PRD 4.1（弹窗形态 Day 4 已定） | 浮在 P1 或 P2 之上 |

**为什么**：

1. 数据只从本地存储读一次，放在内存里，切视图不用重新读、不用重新解析。
2. 不做页面跳转，就没有「跳转后数据没了」的问题（单页应用的根本好处）。

**代价**：浏览器地址栏不会变，所以**没法给某一本书发一个直达链接**。单用户自己用，不需要这个能力。

### 2.8 封面图的加载与回退

PRD 的 AC-3 / AC-4 / AC-5 已经定死了「用户该看到什么」，这里只定**怎么做到**：

| 情况 | 做法 | 对应 AC |
| --- | --- | --- |
| 填了能打开的网址 | 用 `<img>` 加载并显示 | AC-3 |
| 没填网址 | 直接渲染文字占位（书名第一个字） | AC-4 |
| 填了打不开的网址 | 图片的 `onerror` 事件里，把图片换成文字占位 | AC-5 |

**关键澄清**（呼应 PRD 6.3 第 4 条）：封面图的请求是**用户填写的数据**触发的，不是页面自己写死的引用。所以「页面自身不引用任何外部地址」这条约束**不适用于封面图**——PRD 6.3 里已经注明，这里再确认一次。

**兜底原则**：无论因为什么原因加载失败（网址错、网络不通、浏览器拦截），都走同一个回退路径——**不出现破图图标**。

### 2.9 删书时笔记怎么处理

**选：级联删除**——删书时，同步把 `reading:notes` 里 `bookId` 等于这本书的记录一并删掉。

**为什么不选标记删除**（数据留着、界面上不显示）：

1. PRD AC-18 要求「它的笔记也一并消失，别处不残留」。标记删除会让数据留在存储里，与这条验收标准字面冲突。
2. 本地存储容量有限，留着永远不清理的数据是负债。
3. 单用户场景没有「误删要恢复」的强需求。

**代价**：删了就是真删，**没有回收站**。所以 PRD AC-10 要求的那个确认框（并提示会连带删几条笔记）是**唯一的防线**，Day 7 必须实现。

### 2.10 明确不引入的技术

| 不引入 | 为什么 |
| --- | --- |
| 前端框架（Vue / React 等） | 需要 CDN 或构建工具，违反零依赖 |
| CSS 框架（Bootstrap / Tailwind 等） | 同上，且本项目样式量很小 |
| 打包工具（Vite / Webpack 等） | 四个文件的项目，打包是负收益 |
| 后端服务（Node / Express 等） | 2.2 已论证不需要 |
| 数据库（SQLite / MySQL 等） | 同样不需要，第 23 天再议 |
| CDN 上的字体、图标库 | 校园网环境下不可靠；图标用内联 SVG 或文字符号 |
| 任何形式的登录 / 账号系统 | PRD 5.2 的永久边界 |

### 2.11 打开方式与它的前提

**目标用法**：双击 `index.html`，浏览器以 `file://` 的方式打开，不需要启动任何服务。这是选 A 的理由之一——随手记一笔，不该先启动服务。

但 `file://` 和「网页」不是一回事。有两条前提必须写下来，否则 Day 7 会踩：

#### 前提一：localStorage 在 `file://` 下是「未定义行为」，只能靠实测兜住

MDN 对 localStorage 的说明里写着：文档从 `file:` 地址加载时，localStorage 的行为**没有规范定义**，各浏览器可能不同，**不应依赖**。

| 浏览器 | 目前的情况 |
| --- | --- |
| Chrome / Edge | 可用（大概率就是你日常用的），但这是浏览器的宽容，**不是标准给的保证** |
| Firefox / Safari | 对 `file://` 更严格，可能直接不可用 |
| 隐私 / 无痕窗口 | 写入会失败 |

> **有一个结构性的好运**：本设计是**单页 + 三视图**（见 2.7），只有一个 `index.html`——刚好绕开了「每个 `file:` 地址各自独立存储区」的那一半风险。

#### 前提二：不能用 ES Module（这条最容易被顺手踩到）

`file://` 打开的页面，origin 是 `null`。而 ES Module（`import` / `export`、`<script type="module">`）按规定必须经过 CORS 检查——`null` origin 过不了，**加载直接失败，页面一片空白**。

而把 `store.js` 和 `app.js` 用 `import` 连起来，恰恰是最顺手的现代写法。所以这条要提前挡住：

| | 怎么写 | 结果 |
| --- | --- | --- |
| ✗ | 用 `<script type="module">`，两个文件里 `import` / `export` | **双击打开会失败**，必须启动本地服务才跑得起来 |
| ✓ | 两个普通 `<script src>` 按顺序引入（先 `store.js`、后 `app.js`），靠全局共享 | 双击打开可用 |

**代价**：拿不到模块化的作用域隔离，两个脚本共用全局空间。项目只有两个脚本文件、几百行，这个代价可以接受。

> **换个角度说**：这正是 2.5 把存储读写单独关进 `store.js` 的回报——**打开方式如果要换，只影响这两个文件怎么被引入，不影响任何界面逻辑。**

#### Day 7 第一步就要做的事（写在这里防忘）

1. 建一个最小页面，用普通 `<script>` 引入，**双击打开**
2. 往 localStorage 写一条、再读回来，确认能读到
3. **通了** → 按本文档继续；**不通** → 立刻切到退路：用 `python -m http.server` 起一个本地服务打开（那时 ES Module 也就能用了），再继续

> **为什么第一步就做这件事**：这三个功能全都建立在「数据存得住」之上。要是等三个功能都写完才发现存不进去，返工的不是某一段代码，而是整个数据层。
>
> ⚠️ 顺带说明本机情况：**这台电脑已经装了 Python**（Day 1 已确认），所以退路随时可用，不需要临时安装任何东西。

## 3. 数据流图

### 3.1 总图

先回顾路线上的三个点（完整版见 2.1），下面这张图就是**数据在这条路线上怎么走**：

| 环节 | 技术路线 |
| --- | --- |
| 整体形态 | 纯前端应用——没有后端、没有数据库 |
| 页面技术 | 原生 HTML + CSS + JavaScript，零依赖零构建 |
| 数据存储 | 浏览器本地存储（localStorage），两个键 |

![数据流图](./data-flow.svg)

**怎么读**：三个方框、两条双向线。

| 方框 | 角色 | 说明 |
| --- | --- | --- |
| 你 | **数据的唯一来源** | 书、页码、笔记全部由你手填。没有任何一处会自动产生数据 |
| 页面 | 中转站 | 内部两半：**界面**接住你的操作，**数据层**负责格式转换与读写（见 2.5 / 2.6） |
| 本地存储 | **数据的唯一归宿** | 只认两个键：`reading:books`、`reading:notes`（见 2.5） |

**两条线**：向右是**存**，向左是**取**。两条都是双向的——存进去的数据必须能原样读回来，这就是 PRD 6.3 第 3 条「关掉浏览器再打开，数据都还在」在数据流上的样子。

**图上没有的东西，比图上有的东西更重要**：没有服务器、没有数据库、没有第三方接口、没有登录。这不是「暂时没画」，是**本来就不存在**（理由见 2.2）。

### 3.2 三类数据各自的路径

书、进度、笔记走的是**同一条路**，区别只在落在哪个键：

| 数据 | 从哪来 | 经过 | 存进哪个键 |
| --- | --- | --- | --- |
| 书 | 添加 / 编辑弹窗里填的书名、作者、封面网址 | 界面 → 数据层 | `reading:books` |
| 阅读进度 | 详情页填的当前页、总页数 | 界面 → 数据层 | `reading:books`——**进度是书的一部分，不单独存** |
| 笔记 | 详情页的笔记输入框 | 界面 → 数据层 | `reading:notes` |

> **进度百分比不在图上**，因为它不存。按 PRD 3.2 的要求，它由「当前页 ÷ 总页数」实时算出来——存了反而容易和页数对不上。

### 3.3 删除的路径

删除和保存走同一条路，但要多删一样东西：

| 动作 | 数据流 |
| --- | --- |
| 删一条笔记 | 你确认 → 界面 → 数据层从 `reading:notes` 里移除该条 → 界面重新渲染 |
| **删一本书** | 你确认 → 界面 → 数据层从 `reading:books` 移除这本书，**同时**把 `reading:notes` 里 `bookId` 等于它的记录一并移除 → 界面重新渲染 |

> 删书那一行，就是 2.9 选的**级联删除**在数据流上的样子。两条路径都要求先弹确认（PRD AC-10 / AC-22）。

### 3.4 出错时的路径

数据流不是永远顺畅的。三个可能断掉的地方：

| 出错点 | 会发生什么 | 怎么兜 |
| --- | --- | --- |
| 读取失败 | 存储被禁用、或存进去的内容被改坏了，数据层拿不到数据 | 返回可识别的错误，界面给出提示，**不白屏**（PRD AC-23） |
| 写入失败 | 无痕模式下不可写、或容量满，数据存不进去 | 界面**明确提示「没存上」**，不能看起来像存上了 |
| 封面图加载失败 | 图片出不来 | 回退成文字占位，**不出破图**（见 2.8 / PRD AC-5） |

**一条通用原则**：**错误不能静默**。数据没存上、界面却装作存上了，比直接报错更糟——你会在下次打开时才发现东西没了，而且不知道是哪一步丢的。

### 3.5 文字版（同一张图，用文字再讲一遍）

图片万一渲染不出来，看这段——内容和上面那张图完全一样：

## 附录 A · 方案变化时，哪些文件会受影响

**为什么要做这张表**：技术设计的价值不在于「一次选对技术」，而在于**让将来改主意变便宜**。这张表回答一个问题——如果某个决定以后变了，改动会蔓延到哪里。

| 如果这个决定变了 | 要改的文件 | 不用动的文件 | 影响面为什么是这个宽度 |
| --- | --- | --- | --- |
| **存储方案**：本地存储 → 数据库 / 云同步 | `store.js`（改内部实现），可能加一个配置文件 | `index.html` / `styles.css` / `app.js` | 界面**从不直接碰存储**（2.5 的唯一出入口设计） |
| **打开方式**：双击 → 本地服务（或反过来） | `index.html` 里那两个 `<script>` 的写法 | 其余全部 | 换的只是「文件怎么被引入」，不是文件本身（2.11） |
| **页面组织**：三视图切换 → 多页面跳转 | `index.html` + `app.js` | `store.js` / `styles.css` | `store.js` 不认识界面 |
| **样式**：手写 CSS → 引入 CSS 框架 | `styles.css` + `index.html` 的引用 | `store.js` / `app.js` | 样式与数据、逻辑无耦合 |
| **数据字段增加**（例如加「出版社」） | `store.js` 的读写 + `app.js` 的渲染 + `index.html` 的表单 | `styles.css` | 字段是**穿透三层**的东西，改一个字段必然动三处 |
| **状态从三态变四态**（例如加「弃读」） | `app.js` 的筛选逻辑 + `index.html` 的筛选条 | `store.js` 几乎不动 | 状态值本身不改变存储结构 |
| **技术栈整体换代**（原生 → Vue / React） | **全部四个文件** | —— | 唯一承认「推倒重来」的情况，也正是 2.10 提前挡住常见技术的原因 |

**怎么读这张表**：看「要改的文件」这一列的**宽度**。越窄，说明当初的分层越有用。

**最重要的两行**：

- **第 1 行（存储方案）** —— 这是选 A 的全部理由。第 23 天接数据库时，改动被关在 `store.js` 一个文件里，界面一行不用动。
- **第 7 行（整体换代）** —— 唯一「改不动、只能重写」的情况。所以 2.10 才要把框架、构建工具这些提前挡在门外：**不是它们不好，是它们会让后来每一次小改动都变贵**。

> **这张表本身就是"技术设计"的意义**：选型只是第一步，**让改选型变便宜**才是目的。

## 附：术语

| 术语 | 白话解释 |
| --- | --- |
| **前端** | 在用户浏览器里跑的部分：你看到的界面、你点的按钮 |
| **后端** | 在一台服务器上一直跑着的程序，负责处理逻辑、验证身份、读写数据库 |
| **数据库** | 专门用来长期保存数据的程序，通常和后端装在同一台机器上 |
| **纯前端应用** | 整个应用只有前端，没有后端和数据库。打开网页就能用，不需要服务器 |
| **本地存储 / localStorage** | 浏览器自带的一小块存储区，每个网站有独立的一份，关掉浏览器不会消失 |
| **origin（来源）** | 浏览器给每个页面标的「身份」，由协议 + 域名 + 端口三样组成。双击打开的文件走 `file://`，没有域名和端口，身份是空的（`null`）——所以浏览器会拒绝一切需要核对身份的操作 |
| **ES Module（ES 模块）** | JavaScript 官方的「把代码拆成多个文件互相引用」写法，用 `import` / `export` 连接。它有一条硬要求：被引入的文件必须通过「跨来源检查」，所以在 `file://` 下用不了（见 2.11） |
| **JSON** | 一种用文本表示数据的格式，长得像 `{"name": "三体"}`。本地存储只能存文本，所以要先转成它 |
| **序列化** | 把程序里的对象转成可保存的文本格式（这里是转成 JSON）的过程 |
| **单页应用** | 只有一个 HTML 文件，切换内容靠显示/隐藏，不做页面跳转 |
| **级联删除** | 删掉主记录时连带删掉从属于它的记录（这里是删书时连带删笔记） |
| **键值存储** | 按「名字 → 内容」成对保存的存储方式，取数据靠名字 |
